# Database

| | |
|---|---|
| Engine | PostgreSQL 17 on Amazon RDS (`db.t4g` class), encrypted storage |
| Name | `devops94-idp-<env>-svc-${{ values.name }}` (one per environment) |
| Network | private subnets only; reachable only from this environment's ECS tasks |
| Credentials | user `app_admin`; password generated by RDS and kept in Secrets Manager |
| Backups | automated daily + point-in-time recovery (1 day dev/staging, 7 days prod) |

## Schema changes (migrations)

Migrations live in `src/database/migrations` and run **automatically at startup**.

```bash
# add a file like src/database/migrations/<timestamp>-AddOrderStatus.ts
# (class with up() and down(); see 1790000000000-Init.ts)
```

!!! warning "Blue/green needs backward-compatible migrations"
    During a blue/green deployment the **old and the new version run at the same time** against
    the same database. Use **expand → migrate → contract**:

    1. *Expand*: add the new column/table (nullable or with a default). Old code ignores it.
    2. Deploy code that writes both and reads the new one.
    3. *Contract*: in a later release, remove the old column.

    Never rename or drop a column that the currently running version still uses.

## Restore

Point-in-time restore creates a **new** instance (the running one is never overwritten):

```bash
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier devops94-idp-prod-svc-${{ values.name }} \
  --target-db-instance-identifier devops94-idp-prod-svc-${{ values.name }}-restore \
  --restore-time 2026-01-01T10:00:00Z
```

Then validate the data and switch `DB_HOST` through Terraform if it must replace the original.
